## Разделить поиск файлов и полнотекстовый поиск

Статус: запланировано, не реализовано.

### Мотивация

Текущие инструменты заставляют модель работать с двумя разными языками сразу:

- `grep` принимает JavaScript-регулярку и отдельный `glob`, из-за чего модели
  путаются в экранировании, синтаксисе regex и в том, куда класть `*.ts` — в
  `pattern` или в `glob`.
- `glob` принимает произвольный glob (`*`, `**`, `?`) по относительному пути,
  что тоже перегружает модель.

Задача — заменить эту пару на два простых и предсказуемых инструмента:

1. `find_files` — поиск **только по имени файла** с ограниченным DSL.
2. `grep` — полнотекстовый поиск **буквальной подстрокой** без regex и без glob.

Текущий `glob` удалить, а не оставлять рядом: не должно быть двух
перекрывающихся механизмов.

### Решения

- Поиск по имени регистрозависимый по умолчанию; управляется отдельным
  аргументом `caseInsensitive`.
- Оператор отрицания (`!`) в `find_files` в первой версии не добавлять.
- Альтернативы в `grep` не добавлять — при необходимости модель делает
  несколько вызовов.
- `extensions` — массив строк, а не строка с разделителями.

### `find_files`

Название инструмента: `find_files`.

Аргументы:

- `pattern` (`string`, обязательный) — DSL для имени файла:
  - `*` — ноль и более любых символов в пределах одного компонента имени;
  - `?` — ровно один символ;
  - `|` — ИЛИ, самый низкий приоритет;
  - `&` — И, приоритет выше `|`;
  - литералы совпадают сами с собой;
  - `\` экранирует `*`, `?`, `|`, `&`, `\`;
  - скобки в первой версии не поддерживаются.
- `extensions` (`array<string>`, необязательный) — какие расширения искать.
  Пустой/отсутствующий = любые расширения, включая файлы без расширения.
  Нормализовать: убрать ведущую точку, сравнивать с учётом `caseInsensitive`.
- `caseInsensitive` (`boolean`, необязательный) — регистронезависимое
  сравнение и `pattern`, и `extensions`.
- `path` (`string`, необязательный) — подкаталог относительно корня проекта,
  в котором искать. По умолчанию `"."`.
- `maxResults` (`integer`, необязательный) — как в текущем `glob`.

Поведение:

- Ходить через существующий `walkFiles` с теми же `DEFAULT_SKIP_DIRS`.
- `pattern` применять **только к basename**, а не ко всему относительному пути.
  Подкаталог выбирается отдельным `path`.
- Проверку symlink/выхода за проект оставить как в `resolveInsideRoot`.
- Возвращать абсолютные пути, сортировка уже должна быть в `walkFiles`.
- Пустой `pattern` — ошибка.

Парсинг DSL:

- Сначала разбить `pattern` по `|`, но не внутри экранированных участков.
- Каждую альтернативу разбить по `&`.
- Каждый терм скомпилировать в отдельный matcher, где `*` -> «любая
  последовательность», `?` -> «один символ», остальное — литералы.
- Альтернатива считается совпавшей, если совпали **все** термы в ней (`&`).
- Итог — совпадение хотя бы одной альтернативы (`|`).
- При `caseInsensitive` приводить basename и скомпилированный matcher к
  нижнему регистру (учесть, что это упрощённый вариант без полноценного
  locale-aware case folding).

### `grep`

Название оставить `grep`.

Аргументы:

- `pattern` (`string`, обязательный) — **буквальная подстрока**. Это не regex и
  не glob: `*`, `?`, `[` и т.д. — обычные символы.
- `path` (`string`, необязательный) — файл или каталог относительно корня
  проекта. По умолчанию `"."`.
- `caseInsensitive` (`boolean`, необязательный).
- `maxResults` (`integer`, необязательный).

Убрать из `grep` аргумент `glob` — поиск по имени теперь делает `find_files`.

Поведение:

- Использовать строковый поиск (`String.prototype.includes` /
  `Buffer.prototype.indexOf`), а не `RegExp`.
- Оставить построчный вывод `path:line:text`, лимиты на размер файла и
  количество результатов, пропуск бинарных файлов и `DEFAULT_SKIP_DIRS`.
- Оставить symlink/containment-проверку через `resolveInsideRoot`.

## Расширение алгоритмов сжатия контекста диалога

Статус: запланировано; базовое сжатие результатов инструментов (`compactToolMessage`, кнопка «Compact context») реализовано.

### Мотивация

Текущая реализация `compactContext` заменяет вывод завершённых инструментов (`read_file`, `list_dir`, `glob`, `git`, `grep`) на компактные заглушки с числом прочитанных строк или найденных файлов. При длинных сессиях и сложных многошаговых задачах этого становится недостаточно: реплики пользователя и ассистента накапливаются, съедая окно контекста модели.

### Задачи на будущее

1. **LLM Rolling Summarization (Сжатие истории диалога через модель)**:
   - При превышении порога контекста (например, > 80%) или по нажатию кнопки «Compact context» отправлять запрос к модели для краткого структурированного саммаризации ранних раундов (turns) разговора:
     - Какие задачи ставились;
     - Какие ключевые файлы были изменены;
     - Какие архитектурные решения приняты.
   - Заменять старые сообщения `user` и `assistant` на единое системно-структурированное сообщение `[Previous conversation summary]`, сохраняя последние N ходов нетронутыми.

2. **Локальный эвристический / семантический анализатор контекста**:
   - Анализ зависимостей между вызовами инструментов:
     - Если файл был прочитан (`read_file`), а затем полностью перезаписан (`write_file`), ранний вывод `read_file` и промежуточные diff'ы можно безопасно отбрасывать.
     - Если один и тот же файл читался повторно без изменений, сохранять только последнее чтение.
   - Дедупликация и сжатие повторяющихся результатов `list_dir` / `glob` при отсутствии изменений в файловой структуре.
