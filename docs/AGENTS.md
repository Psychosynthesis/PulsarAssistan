# Инструкции для агентов

Руководство для ИИ-агентов и участников, работающих над этим пакетом.

Описание полного цикла разработки функций или исправления ошибок см. в описании навыка `feature-dev` по адресу:
`.github/skills/feature-dev/SKILL.md`.

## Архитектура

Модули в директории `src/`, собираемые в `lib/` с помощью `build.mjs` (esbuild):

- `main.ts` — точка входа Pulsar: команды, opener, десериализатор, миграция реестра, status-bar. Какие панели открыты, не пишется в `config.cson`. Явный allowlist `projects` (allowCommands / testCommand) — да, в пользовательском конфиге, не в дереве проекта.
- `session/agent-session.ts` — для `type: acp` JSON-RPC по stdio; для `type: openai` прямой `BuiltinAgent` без ACP-транспорта. Cwd инжектится; `atom.project` не читается. Нет `terminal/*`.
- `builtin/` — OpenAI-совместимый агент (HTTP). `git` всегда; `run_command` / `run_tests` только по политике проекта.
- `project-policy.ts` — разбор `pulsar-assistant.projects`.
- `view/` — UI панели и glue для `atom.config`. Пикер группирует API и ACP.
- `agent-config.ts` / `openai-client.ts` / `grep.ts` / `project-uri.ts` / `util.ts` — чистые модули для тестов. `type: command` читается как `acp`.

Порядок работы: `main` открывает `PulsarAssistantView` для корневой директории проекта → представление (view) управляет экземпляром `AgentSession`, привязанным к этому корню → сессия либо вызывает `BuiltinAgent` напрямую, либо поднимает ACP CLI по stdio → представление отображает события.

## Принципы

- **Обсуждение перед написанием кода.** Никогда не начинайте писать код, не обсудив подход и не получив согласия разработчика.
Если возможно несколько вариантов решения, сначала разберите плюсы и минусы каждого из них и согласуйте направление действий.
Прежде чем рекомендовать какой-либо подход, убедитесь, что он соответствует текущему механизму протокола и принятой в Zed практике реализации.
- **Будьте думающим коллегой, а не тем, кто во всем соглашается.** Не принимайте предложения разработчика слепо.
Если идея кажется ошибочной, рискованной, излишне усложненной, несогласованной с ACP/Pulsar или не являющейся оптимальным минимальным решением,
прямо скажите об этом и объясните причину. Предложите более удачный и простой путь. Соглашайтесь, если предложение обосновано;
возражайте, только если есть конкретные причины.
- **Придерживайтесь минимализма.** Отдавайте предпочтение минимальным изменениям,
которые полностью решают проблему. Избегайте введения новых зависимостей,
абстракций и настроек без явной необходимости. Пишите краткие и четкие сообщения коммитов, записи в журнале изменений и обновления
документации — без лишних слов.
- **Следуйте стандартам и практикам Pulsar.** Придерживайтесь соглашений, используемых ядром Pulsar и его пакетами
(Octicons, команды, схема конфигурации, элементы панели, привязки клавиш, меню, API `atom`/Pulsar). В случае сомнений смотри, как это
реализовано в существующих пакетах Pulsar.
- **Обеспечивайте поддержку как минимум двух платформ.** Пакет должен работать в Windows и Linux, а агент ACP может быть запущен
в любой из этих систем. Отдавайте предпочтение кроссплатформенным API (используйте модуль `path` для разделителей путей, никогда
не прописывайте жестко `/` или `\`), запускайте дочерние процессы с помощью `cross-spawn` (чтобы корректно обрабатывались
Windows-оболочки `.cmd`/`.ps1`/`.bat` без использования `shell: true`) и учитывайте различия в символах переноса строк в разных ОС.
- **Используйте пространства имен для публичных идентификаторов.** Добавляйте префикс `pulsar-assistant` или `PulsarAssistant` к командам, URI, десериализаторам, CSS-классам и меткам логов, чтобы избежать конфликтов с ядром Pulsar или другими пакетами.
- **Разберитесь в SDK перед использованием.** Изучите, как на самом деле работает `@agentclientprotocol/sdk` (посмотрите типы и экспортируемые элементы в `node_modules`), вместо того чтобы строить догадки.
- **Изучите документацию ACP.** Сверяйте поведение протокола с документацией и схемой Agent Client Protocol: https://agentclientprotocol.com
- **Ориентируйтесь на существующие ACP-клиенты.** При проектировании поведения клиента анализируйте, как решают аналогичные задачи Zed и другие редакторы с поддержкой ACP, а также обращайтесь к документации протокола и исходному коду `@agentclientprotocol/sdk`. Отдавайте предпочтение проверенным решениям из этих источников, а не изобретайте собственные.
- **Используйте актуальные механизмы протокола.** В ACP иногда предусмотрено несколько способов выполнения одной и той же задачи (например, режимы сеанса против параметра конфигурации `mode`). В схеме отмечены устаревшие и нестабильные элементы API — учитывайте это и опирайтесь на актуальные механизмы, а не на устаревшие. Если вы обнаружили, что создаете два дублирующих друг друга механизма, один из которых приходится скрывать, остановитесь и пересмотрите подход.
- **Уделяйте внимание безопасности.** При внесении любых изменений оценивайте их влияние на безопасность: не допускайте появления кода, который может привести к утечке секретных данных, ослабить изоляцию (песочницу), довериться непроверенным входным данным или неоправданно расширить поверхность атаки.

## Чек-лист для проверки

При проверке изменений уделите особое внимание следующим пунктам:
- **Мертвый код и устаревшие элементы** — отсутствие неиспользуемых импортов, переменных, методов, веток кода, CSS, команд, конфигурации, документации или оставшихся сгенерированных артефактов.
- **Минимализм** — минимально необходимые завершенные изменения; отсутствие переписывания кода, не относящегося к задаче, а также лишних абстракций, зависимостей или настроек. Всегда помним про DRY, KISS и YAGNI.
- **Соответствие Pulsar** — интерфейс и поведение соответствуют существующим пакетам Pulsar: Octicons, переменным тем/Less, командам, схеме конфигурации, элементам панели (dock), привязкам клавиш, меню и API `atom`/Pulsar.
- **Корректность ACP** — поведение протокола соответствует документации/схеме ACP и фактическим типам/исходному коду `@agentclientprotocol/sdk`; не делайте предположений о полях или возможностях, не описанных явно.
- **Эталонное поведение** — для элементов интерфейса или решений о жизненном цикле, зависящих от протокола, сравнивайте реализацию с Zed или другим клиентом, поддерживающим ACP, и обоснуйте намеренные расхождения.
- **Полнота реализации и жизненный цикл** — подключены все необходимые компоненты; корректно обрабатываются и очищаются (освобождаются ресурсы) граничные случаи, объекты `Disposable`, узлы DOM, сессии, дочерние процессы, таймеры и слушатели событий.
- **Безопасность на разных платформах** — корректная работа с путями (Windows/macOS/Linux), запуском процессов и символами переноса строк; используйте `path` и `cross-spawn`, не используйте жестко закодированные разделители.
- **Безопасность** — отсутствие утечек секретных данных, безопасный рендеринг контента, управляемого агентом, отсутствие небезопасного запуска процессов, ослабления песочницы или обработки непроверенных входных данных от агента.
- **Валидация и обработка ошибок** — выполнение или обновление соответствующих проверок/тестов; ошибки должны быть явно видны (никаких «тихих» возвратов, перехвата всех исключений или фоллбэков, маскирующих сбой под успех).
- **UX, производительность и совместимость** — учтены поведение клавиатуры и фокуса, соответствие теме оформления, переполнение (overflow), ограничение объема вывода/роста DOM, совместимость конфигурации/состояния и поддержка возможностей старых версий агента.
- **Сгенерированные файлы и документация** — `lib/main.js` соответствует результату сборки; обновлены README, список изменений (changelog), документация по функциям и соответствующие уведомления.

## Рабочий процесс

- Вносите изменения в `src/`, затем пересобирайте проект: `npm run build` (или `npm run watch`).
- Поддерживайте сборку в рабочем состоянии: проверка типов (`npm run typecheck`) должна проходить успешно. - `npm test` запускает `node --test` для файлов `test/*.mjs`. Тесты импортируют собранный файл `lib/util.js`, а не исходный код из `src/`, поэтому сначала выполните сборку. Запуск отдельного теста: `node --test test/util.test.mjs` (можно добавить `--test-name-pattern="..."` для фильтрации).
- `npm run smoke -- <команда...>` выполняет реальное рукопожатие ACP с настоящим агентом (`scripts/smoke.mjs`); по умолчанию используется `copilot --acp --stdio`.
- `scripts/mock-agent.mjs` принудительно активирует выбор метода аутентификации (reactive-auth) с двумя доступными методами. Проверьте работу с помощью `npm run smoke -- node scripts/mock-agent.mjs`; установите `MOCK_AUTH_METHODS=1` для использования одного метода или `MOCK_NO_AUTH=1` для пропуска аутентификации.
- Закоммиченный бандл `lib/main.js` должен соответствовать результату сборки (это контролируется в CI).
- **Перед завершением работы над любыми изменениями проверьте, не требуют ли обновления следующие файлы (или любые другие):**
- `CHANGELOG.md` — добавление, изменение или удаление функций, видимых пользователю
- `README.md` — описание функций, параметры конфигурации, инструкции по использованию
- `AGENTS.md` — изменения, затрагивающие рекомендации для контрибьюторов или агентов
- **По завершении задачи критически оцените незакоммиченные изменения**
(`git diff` / `git status`), сверяясь с приведенным выше чек-листом, прежде чем отчитываться о результатах. Проверьте каждый найденный момент в коде; сообщайте о реальных проблемах, а не о незначительных деталях.
- **Не коммитим в master напрямую без явного указания.** Если поступил запрос на коммит в master, остановись и уточни.
